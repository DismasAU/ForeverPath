# ForeverPath architecture

## Layout

```

  ForeverPath.toc            manifest (Interface 16001); ForeverPath_Camelot.toc is an identical copy
  Core/
    Namespace.lua            shared `ns` table, version, the single global `ForeverPath`
    Util.lua                 pure helpers (parsing, defaults, copies, time formatting)
    Log.lua                  chat output, debug flag, error capture, protected calls
    Compat.lua               WoW API discovery; the only file that asks "which client is this?"
    Events.lua               game event registration + internal FP_* message bus, debounce, combat deferral
    Database.lua             SavedVariables defaults, migrations, loading
    GoalService.lua          application service: GoalStore instance + "input text -> goal"
    SlashCommands.lua        /fp
    Bootstrap.lua            ADDON_LOADED wiring (loads last)
  Domain/                    pure Lua, no WoW API access
    Status.lua               evaluation statuses and labels

    GoalModel.lua            generic goal shape, types registry, ids, validation

    ItemClasses.lua          classID/subclassID -> gathering / drop hints
  UI/

    Screens/CraftingTree.lua screen 03: dependency tree tab (tree panel + selected node)
    Screens/CraftWise.lua    screen 04: strategy cards, breakdown table, "Use this plan"
    Screens/Crafting.lua     screen 02: hero panel, tabs, requirements table
    Screens/Quests.lua       quests by zone / goal / completed, details, chain, rewards
    Screens/Equipment.lua    slots, GearQuest picks, stat comparison, targets as goals
    Screens/Reputations.lua  factions by group, standing, target, quests, rewards
    Screens/Characters.lua   screen 07: character cards, coverage banner, account-wide scope
    Screens/Shopping.lua     screen 05: goal chips, summary, filter tabs, bought ticks, send to chat
    Screens/Attunements.lua  screen 06: picker, header, step timeline, current step
    MainFrame.lua            shell: window, header, sidebar, status bar, screen switching, link hook
    Tracker.lua              screen 08: compact goal tracker (separate frame)
  Domain/Overview.lua        dashboard aggregation (missing materials, next steps) - pure
  Domain/ShoppingList.lua    cross-goal shopping rows, categories, mail plan, chat lines - pure
  Domain/CraftWise.lua       buy / craft / hybrid comparison over a full tree, route plan, presets - pure
  Core/GoalCompletion.lua    auto-completes item goals from bag counts (baseline + peak gain), celebrates
  UI/Toast.lua               queued celebration toast at the top of the screen

```

Screens register themselves in `ns.UI.Screens[key] = { label, Create(parent, key) }`
and expose `screen:Refresh()`. `MainFrame.Refresh` re-evaluates every open goal
once (`Planner.EvaluateAll` into `MainFrame.views`) and then refreshes the
visible screen and the tracker, so a goal is never planned twice per refresh.

Every file receives `(addonName, ns)` through `...`. Nothing is global except
`ForeverPath` (the namespace, for `/dump` and integrations) and the addon
compartment click handler the TOC requires.

## Rules

1. UI files only render view models and call `GoalService` / providers. They
   never compute requirements.
2. Domain files never call the WoW API. They receive plain tables and
   functions. This is what makes them testable without the client.
3. Providers convert API results into normalized tables **once**
   (`RecipeModel.FromSchematic`, `ItemProvider.GetItem`,
   `InventoryProvider.GetCounts`). Raw API tables do not travel further.
4. `Core/Compat.lua` resolves every API function the addon uses, modern
   namespace first, legacy global second, `nil` if neither exists. Everything
   else checks the resolved capability instead of probing globals.
5. Event handlers run through `Log.Call` (xpcall). Errors are recorded in
   `Log.errors` and shown once, never swallowed.
6. Refreshes are event driven and debounced; nothing runs OnUpdate.

## Data flow

```
player input ("2996", item link, "Linen Bag")
   |  SearchBox / slash command
   v
GoalService.AddFromInput  --ItemProvider.ParseInput / SearchByName / Exists-->  itemID
   |  GoalStore:Create / SetQuantity / Select      (writes ForeverPathCharDB.goals)
   v
FP_GOALS_CHANGED  ---->  MainFrame.RequestRefresh (debounced)
                             |
                             v
                   GoalDetails.Refresh(goal)
                             |
                             v
                   Planner.Evaluate(goal, deps)
                      |- ItemProvider.GetItem(itemID)              exists? loaded? name/icon
                      |- ProfessionProvider.FindRecipesForItem     cached recipes + learned flags
                      |- ProfessionProvider.GetRecipe(id, true)    live schematic when available
                      |- DependencyResolver.Resolve(recipe, qty)   tree; claims inventory via the ledger
                      |     |- findRecipes(reagentID) for every missing reagent (recursion)
                      |     |- Allocation ledger shared by all goals in EvaluateAll
                      |- CraftingEngine.BuildPlan(recipe, qty, DirectCounts(tree))
                      v
                   view { status, message, item, recipe, plan, tree, inventoryNote, progress }
                             |
                             v
                   MaterialList.SetMaterials(plan.materials)
```

Recipe data arrives independently of goals: whenever a profession window is
open, `TRADE_SKILL_LIST_UPDATE` (debounced) triggers
`ProfessionProvider.ScanOpenProfession`, which walks `GetAllRecipeIDs()` in
chunks of 40 per frame, normalizes each schematic and stores it in
`ForeverPathDB.recipes` with an `itemRecipes[outputItemID]` index. The
per-character `knownRecipes` table records the learned flag. `FP_RECIPES_UPDATED`
then refreshes the window.

Inventory: `BAG_UPDATE_DELAYED` marks the bag index dirty; the next lookup
rescans all bag slots once. The bank is scanned while `BANKFRAME_OPENED` and
stored as a timestamped snapshot in `ForeverPathCharDB.bankCache`.

## Internal messages

| Message | Payload | Emitted by |
|---|---|---|
| `FP_READY` | - | Bootstrap after database and providers initialise |
| `FP_GOALS_CHANGED` | event (`added`/`removed`/`selected`/`updated`), goal | GoalStore via GoalService |
| `FP_RECIPES_UPDATED` | professionID or nil | ProfessionProvider |
| `FP_INVENTORY_UPDATED` | - | InventoryProvider |
| `FP_ITEM_LOADED` | itemID, success | ItemProvider |
| `FP_CHARACTERS_UPDATED` | key | CharacterProvider after a snapshot or removal |
| `FP_SOURCES_UPDATED` | "vendor" + npc, or "atlasloot" | VendorProvider after a merchant scan; SourceProvider when the AtlasLoot index is ready |
| (listener) `FP_INVENTORY_UPDATED`, `FP_GOALS_CHANGED` | | GoalCompletion checks open item goals after every bag change, baselines new goals and re-baselines reopened ones |

## Normalized models

Recipe (`ForeverPathDB.recipes[recipeID]`):

```lua
{ recipeID, name, icon, outputItemID, quantityMin, quantityMax, recipeType,
  professionID, professionName, source = "C_TradeSkillUI", scannedAt,
  reagents = { { itemID, quantity, slotIndex, alternatives = { itemID... } | nil } } }
```

Only required *basic* reagent slots are kept; optional, finishing and
modifying reagents are not needed to craft and are ignored for now.
Multi-quality reagent slots keep the first candidate as `itemID` and the rest
as `alternatives`.

Goal (`ForeverPathCharDB.goals[id]`):

```lua
{ id = "fp-<time>-<n>-<rand>", type = "CRAFT_ITEM" | "OBTAIN_ITEM", status = "ACTIVE" | "QUEUED" | "PAUSED" | "COMPLETED",
  target = { itemID, quantity }, tracked = true, priority = 1,
  createdAt, updatedAt, completedAt, notes }
```

Open goals (not COMPLETED) carry sequential priorities; `GoalStore:List(filter)`
orders by status group, priority, then creation time. The tracker and the
header pill follow `GoalService.TrackedGoals()` (open and tracked).

`goal.routes` (optional) maps a reagent itemID to `"craft"` or `"buy"` and
overrides the resolver's default (craft when a learned recipe exists, else
buy). `GoalStore:SetRoute(id, itemID, route|nil)` edits it.

## Dependency tree

`DependencyResolver.Resolve({ recipe, quantity }, opts)` returns

```lua
tree = { root = node, byKey = { [key] = node }, ledger, summary }
node = { key = "4238>2996>2589", itemID, depth, parentKey, quantity, perCraft,
         owned, ownedBags, ownedBank, available, availableBags, availableBank, reserved,
         missing, status = "root"|"have"|"partial"|"missing",
         options = { { kind = "craft", recipe, learned, professionName, yield, cycle }, { kind = "buy" }, ... },
         route = "craft"|"buy"|<hint kind>, routeSource = "root"|"default"|"override",
         craft = { recipe, crafts, yield, expectedOutput, surplus, learned, professionName } | nil,
         children = { node... }, blocked = nil|"cycle"|"depth"|"no-recipe" }
summary = { nodes, resolved, missingLeaves = { { itemID, count, route, professionName, recipeLearned } },
            crafts = { { itemID, crafts, expectedOutput, professionName, learned, ready } }, maxDepth, blocked }
```

Nodes are visited depth-first in reagent order and claim inventory from the
`Allocation` ledger as they go, so an item that appears twice in a tree (or in
two goals) is only counted once. `owned` is what this node received (capped at
its need); `available` is what was free before it claimed, which is what the
UI shows as "Have". `DependencyResolver.DirectCounts(tree)` feeds the depth-1
availability back into `CraftingEngine.BuildPlan` so the flat Requirements
table agrees with the tree. `Flatten(tree, { collapsed, unresolvedOnly })`
produces the rows the tree tab draws, with guide-line information per row.

`Planner.EvaluateAll(goals)` creates one ledger and evaluates goals in list
order (ACTIVE by priority, then QUEUED, then PAUSED), which is the allocation
order.

## Characters

`CharacterProvider.Snapshot()` writes `ForeverPathDB.characters[key]`:

```lua
{ key = "Name-Realm", name, realm, level, class, classFile, race, gold, lastSeen,
  bags = { items = { [itemID] = count }, scannedAt }, bank = { items, scannedAt } | nil,
  professions = { { name, skillLevel, maxSkillLevel, skillLine } },
  knownRecipes = { [recipeID] = true }, goals = { { id, title, status, itemID } } }
```

Readers never see the current character as an alt. `Alts(itemID)` /
`AltTotal` feed `InventoryProvider.GetCounts().alts`; `CanCraft(itemID)`
checks alts' `knownRecipes` against `itemRecipes`; `Sources(itemID)` turns
both into resolver hints; `BestCoverage(needs)` drives the Characters banner.
The ledger draws bags, then bank, then alts, and only touches alts when
`settings.includeAlts` is true.

`GoalModel.Types` registers CRAFT_ITEM, OBTAIN_ITEM, COMPLETE_ATTUNEMENT
(targets `{ attuneID, name, icon }`), LEARN_RECIPE (`{ spellID, name,
professionName, professionID, icon }`), REACH_SKILL (`{ professionID,
professionName, rank, startRank, icon }`), COMPLETE_QUEST (`{ questID,
name, level, instance, icon }`), REACH_REPUTATION (`{ factionID, name,
standing, startValue, icon }`) and APPLY_ENCHANT (`{ spellID, name,
professionName, professionID, icon, quantity, casts }`), all supported.
`target` is type specific.

**Enchant planning.** The catalogue keeps enchants (and tinkers) as recipes
with no output item: `Recipes.Get` returns `enchant = true`, `outputItemID
= nil`, `quantityMin = 1`, `recipeType = 3`; `Recipes.Index` / `Lookup`
skip them, `Recipes.IsEnchant(spellID)` and `Search(text, limit,
profession, kind)` find them. `RecipeModel.FromSchematic` accepts a
schematic without an item when `recipeType` is 3 or `opts.isEnchant`
(the catalogue) says so, so profession scans record known enchants
(`ProfessionProvider` never indexes them by item). `Planner.EvaluateEnchant`
resolves `Resolve({ recipe = <enchant>, quantity = casts left, learned })`:
the root (`enchant:<spellID>`, `node.enchant = { recipe, learned }`,
`node.name` / `node.icon`, never claims) gets `craft` with `enchant = true`
and one cast per unit, and `expand` adds the formula child (`learn`), a
train step while unlearned, and the reagents. The flat plan is
`CraftingEngine.BuildPlan` over the reagents with `plan.enchant`,
`plan.castsDone`, `plan.stepsMissing`, and `isComplete` only when the
formula or training is also resolved. The view carries `enchant = {
recipe, learned, knownBy, profession, need, have, skillOK, blocked, kind,
teachItemID, trainer, casts, quantity, remaining }` and `nextStep`.
`GoalCompletion.RecordCast(spellID)` (from `UNIT_SPELLCAST_SUCCEEDED` for
the player) increments `target.casts` on every open enchant goal for the
spell and completes the goal at `quantity`; reopening resets the count.
Skill-plan craft nodes (`forSkill`) and enchant roots have no `itemID`:
they carry `name` / `icon`, `Summarize` lists crafts with `name` and
`enchant`, and screens use `displayOf` / `labelOf` fallbacks.

**Reputation planning.** `Providers/ReputationProvider.lua` normalises
`C_Reputation.GetFactionDataByIndex` / `GetFactionDataByID` (or the legacy
tuples) into `{ factionID, name, standing (1..8), standingLabel, value,
min, max, into, span, percentWithin, header }` (`List()`, cached until
`UPDATE_FACTION`; `Get(factionID)`), with `StandingMin` / `StandingMax`
for the classic thresholds, `StandingByName`, `Progress(factionID, target,
startValue)` (`remaining`, `reached`, `percent` anchored at the goal's
start) and `NextStanding`. Ways to earn: `QuestRewards()` parses the
journal entries' reward texts ("<Faction> +N") through QuestProvider;
`QuestsFor(name)` adds live states. `Rewards(factionID)` reads
AtlasLootClassic_Factions (`EnsureAtlas` loads the module once through
AtlasLoot's loader, `IndexAtlas` maps each tier to a standing by its label
or its position) and `SoldBy(itemID)` / `Hints(itemID)` turn them into
vendor options for the resolver, `unavailable` with the reason below the
standing. `Planner.EvaluateReputation` carries `reputation = { record,
progress, quests, rewards, targetLabel }`, `nextStep` (the first open quest
that gives reputation) and a `StepPlan`; `GoalCompletion` finishes the goal
on `UPDATE_FACTION`.

**Equipment.** `Providers/EquipmentProvider.lua` is a read-only view, not a
goal type: `SLOTS` (display order, inventory slot ids, GearQuest slot names,
equip locations), `Equipped()` (ids and links per slot, names and icons
through ItemProvider, item levels), `Stats(linkOrID)` (client item stats
normalised to short keys, GearQuest's `scoredStats` as a fallback),
`SlotKeysFor(itemID)` (from the equip location), `Candidates(slotKey, {
source })` (GearQuest's `Data.entries` after `EnsureClassLoaded`, filtered
by class, `Spec:GetDisplaySpec`, faction and the level band, best rank per
item, with the facts from the `<class>ItemFacts` tables), `Hints(itemID)`
(resolver source hints from those facts, merged into
`SourceProvider.Sources` after the journal and AtlasLoot) and `Analyze({
source, goals, views })` (per slot: equipped, candidates, best, status
bis / upgrade / empty / none, the open item goal whose item fits the slot).
The Equipment screen is a consumer of `Analyze`; a target becomes a
CRAFT_ITEM or OBTAIN_ITEM goal through `GoalService.AddItemGoal`.
`FP_EQUIPMENT_UPDATED` follows the equipment events.

**Quest planning.** `Providers/QuestProvider.lua` builds a static index
(`Index()`, lazily, dropped on `FP_READY`) from ForeverDungeonJournal
(`DB[dungeon].quests`, `QUEST_PREREQ_CHAINS`, `QUEST_START_MAPS`,
`FOREVER_QUEST_XP_FALLBACK`; chain prerequisites that are not dungeon
quests get `source = "chain"` entries) and Attune (`Attune_Data.quests`,
`questGivers`, `questRewards`, the step that uses the quest for the
attunement name and location). Live state is `State(questID)`: completed
flag, in log, ready (`C_QuestLog.IsComplete`), log index, title and level
from `GetInfo`, objectives from `GetQuestObjectives`, and a 0..1 fraction.
`LogEntries()` walks the log with its zone headers; `Name()` falls back to
`GetTitleForQuestID` after `RequestLoadQuestByID` (`QUEST_DATA_LOAD_RESULT`
fills `titles`); `Chain()` is the prerequisites then the quest, each with
its state, and the first incomplete one; `StateLabel()` gives Ready / In
log / Available / Locked / Done; `FeedsGoals(goals, views)` maps quests to
the open goals whose missing leaves they reward. `Planner.EvaluateQuest`
carries `quest = { entry, state, chain, next, label, levelBlocked }`,
`nextStep`, a `StepPlan` and progress = completed chain quests plus the
objective fraction of the one in the log. The quest events (accepted,
turned in, removed, log update) fire `FP_QUESTS_UPDATED` (debounced);
`GoalCompletion` completes the goal when the flag is set.

**Questlines.** `AttuneProvider.QuestlineFor(questID)` picks the
attunement (class chains first) whose steps include the quest, for this
faction and class (`AttunementsWithQuest`), runs `Progress` and keeps the
steps the quest's step follows transitively (`FOLLOWS` parts split on `&`,
each part "a|b" either-of; once one alternative of a stage is done the
others leave the line): `{ attune, steps, target, next, done, total,
percent, complete }`. `QuestProvider.Questline` adds each quest step's
entry and live state. `QuestProvider.Giver / Turnin` read
`QuestFactsProvider.Get` (learned facts over the shipped catalogue), then
the journal/Attune start pin, then the pickup text; `RequiredItems` are the
live item objectives (`QuestFactsProvider.LiveItems`: `ParseObjective`
then an exact name match through `ItemProvider.SearchByName`) or the
recorded ones; `Waypoint` is the giver (not yet taken) or the turn-in
(ready). `Planner.QuestStepText` phrases a step ("Pick up X from Y in Z",
"Finish X: progress", "Turn in X to Y"), `Planner.QuestlineItems` sums the
items of the line's open quests, and `Planner.RewardQuestline(itemID)`
finds the quest that rewards an item and its line. `EvaluateQuest` plans
along the line (progress, label Locked while the chain is ahead of the
quest, a quest-step tree whose children are the items) and `EvaluateObtain`
attaches the items below the reward (`DependencyResolver.AttachItems`;
the reward stays a missing leaf through `questParent`) and sets
`view.questline`, `view.nextStep` and `view.waypoint`. The learner
(`QuestFactsProvider.Init`) records on `QUEST_DETAIL`, `QUEST_ACCEPTED`
(retrying unresolved names on `QUEST_LOG_UPDATE` / `BAG_UPDATE_DELAYED`
after asking the client for every bag item's name) and `QUEST_COMPLETE`,
and fires `FP_QUEST_FACTS_UPDATED`.

**Learn-recipe planning.** `Planner.EvaluateLearn` looks the recipe up
(`Planner.RecipeByID`: catalogue, then a recorded window), checks
`ProfessionProvider.IsLearned`, this character's standing in the profession
(`Planner.CurrentSkill`: the live profession list, else a recorded window)
and `CharacterProvider.WhoKnows` for alts. A pattern recipe resolves an
obtain tree of the teaching item (`Resolve({ itemID, quantity = 1, learn =
true, learnFor })`); a trainer recipe resolves a one-node tree whose root is
the step (`Resolve({ step = { kind = "train", ... } })`) and a `StepPlan`
with no materials. The view carries `learn = { recipe, learned, knownBy,
profession, need, have, skillOK, blocked ("profession" | "skill"), kind
("plans" | "trainer" | "combine"), teachItemID, trainer }` and `nextStep`.
`GoalCompletion` completes it on `FP_RECIPES_UPDATED`.

**Reach-skill planning.** `Planner.EvaluateSkill` reads the standing, builds
candidates (`Planner.SkillCandidates`: every catalogue recipe of the
profession with thresholds, learned flag, `learnable` when the requirement
is known from a recorded trainer rank or a pattern whose item carries it,
reagent cost from `PriceProvider` when every reagent is priced, reagent
count) and hands them to `SkillPlanner.Plan(current, target, candidates)`:
per point the best recipe (learned first; by expected cost when priced,
else by expected crafts `1 / chance` then reagent count), merged into
segments with crafts rounded up, gaps where nothing applies. The resolver
lays it out from `Resolve({ step = { kind = "skill" }, crafts = { { recipe,
crafts, learned, from, to } } })`: the root is a step (`skillRoot`, not
counted as a dependency), each craft a `forSkill` node (claims nothing,
route `craft`, fixed craft count, no options) that expands like any craft,
so unlearned recipes get their pattern child or train step. The flat plan
is `Planner.SkillMaterials` (depth-2 reagents merged by item). The view
carries `skill = { professionName, current, target, start, max, percent,
reached, scanned, capBlocked }`, `skillPlan`, `nextStep`; `Overview.Percent`
reads `skill.percent`. The shopping list skips `forSkill` nodes and lists a
train step that is a tree root; CraftWise never prices buying a `forSkill`
output. `GoalCompletion` completes it on `SKILL_LINES_CHANGED`.
`GoalService.TypeForItem` picks between the two item types when a goal is
added without one: crafting when a recipe is recorded (or nothing has been
scanned yet), obtain otherwise; `GoalStore:SetType` switches them.

**Obtain planning.** `Planner.EvaluateObtain` runs for OBTAIN_ITEM goals and
for CRAFT_ITEM goals with no recipe but at least one known source. It
resolves `DependencyResolver.Resolve({ itemID, quantity })`: the root is the
item itself, `node.claims` is true (it takes inventory through the ledger,
counts as a node and a missing leaf, appears in the shopping list) and its
route comes from `RouteRank` over the source hints, or "craft" when a
learned recipe exists, in which case only the shortfall expands. The view
carries `obtain = true`, `sources`, `hint` (the chosen source) and
`sourceText`; `view.plan` is either the craft plan of the shortfall or
`Planner.ObtainPlan` (one material: the item), so every screen that reads
`plan.materials` works unchanged. Crafting-tree roots keep `claims = nil`
and the UI's `isCraftRoot(node)` distinguishes the two.

Plan (output of `CraftingEngine.BuildPlan`):

```lua
{ recipeID, outputItemID, quantityWanted, craftsNeeded, outputPerCraft, outputPerCraftMax,
  expectedOutput, isComplete,
  materials = { { itemID, perCraft, required, owned, ownedBags, ownedBank, bankSource, missing, alternatives } },
  totals = { required, owned, missing, materialsMissing } }
```

Crafts are computed from the recipe's guaranteed minimum yield, so random-yield
recipes are never under-provisioned.

## SavedVariables

- `ForeverPathDB` (account): `schemaVersion`, `settings` (`debug`,
  `includeBank`, `includeAlts`), `recipes`, `itemRecipes`, `itemNames`,
  `characters`, `vendors`, `trainers`, `trainerNPCs`, `questFacts`
  (questID -> `{ giver, turnin, items, itemsAt }`).
- `ForeverPathCharDB` (character): `schemaVersion`, `goals`, `selectedGoalId`,
  `knownRecipes`, `professions`, `bankCache`, `window`, `tracker`, `ui`,
  `shopping` (`bought`, `included`, `sort`, `filter`).

Schema 2 (0.2.0) moved `window` to the character table and added the goal
fields above; `Database.migrations` carries the upgrade and `Database.Load`
copies a v1 account-wide window into the character table once.

`Database.Prepare` runs ordered migrations (`Database.migrations.global/char`,
entries `{ version, up }`) against the stored shape, then fills defaults. Data
written by a newer schema is left untouched. `GoalStore.New` drops malformed
goals on load and reports the count.

## Extension points

- **New goal types**: add an entry to `GoalModel.Types` and a validator, then
  a branch in `Planner.Evaluate` (or a per-type planner table). Screens are
  declared in `MainFrame.Nav`; `MainFrame.OpenGoal` maps a goal type to
  the screen that plans it (attunements, quests, reputations), everything
  else (items, recipes, skills, enchants) opens on Crafting.
- **Type-ahead**: `GoalService.Suggest(kind, text, limit)` returns hits
  `{ kind, text, meta, add(quantity) }` for one goal kind or "all";
  `MainFrame.ShowSuggestions(box, hits, { quantity, onAdd })` renders the
  popup under any input (the header search and the New Goal bar use it).
- **Unmet factions**: `Catalogue.factions[id] = { name, parent, index,
  expansion, { raceLow, raceHigh, classMask, base, ... } }` from the
  client's Faction table; `ReputationProvider.StartingValue(row, raceID,
  classID)` applies the client's slot rule, `Unmet(factionID)` builds a
  record with `unmet = true`, and `Get` / `Search` fall back to it.
- **Links**: `MainFrame.InstallLinkHook` accepts item, enchant and spell
  links; `GoalService.SpellIDFromText` reads the spell id and
  `AddFromInput` routes an enchant to `AddEnchantGoal` and an item recipe
  to the item it makes.
- **Recipe catalogue**: `Data/RecipeCatalogue.lua` is generated from the
  client's own tables (`tools/DbExtract`, see its README) and decoded by
  `Data/Recipes.lua`. `Planner.Candidates` merges recorded recipes with the
  catalogue (recorded first, deduplicated by spell id; a catalogue recipe this
  character has learned counts as learned). In the resolver an unlearned
  catalogue recipe goes through `qualifyCraft`: `opts.crafters(professionName)`
  (`CharacterProvider.WithProfession`: this character live, then alt
  snapshots) names who could craft it at `recipe.skill.min`, or marks the
  option `unavailable` with the reason. Route choice: a learned recipe wins
  as before; otherwise `combine` (an item-use recipe, anyone) ranks with alt
  crafting, `learn` (someone could learn it) just above the Auction House,
  and a craft nobody can do is only laid out when nothing else exists, which
  is the case for soulbound items (`opts.soulbound(itemID)` from the
  catalogue's binding flag marks buy / alt / altcraft unavailable;
  `node.noRoute` when nothing at all is left). A craft node carries
  `craft.crafter`, `craft.unavailable`, `craft.combine`, `craft.teachItemID`;
  the plans item becomes a child node (`node.learn`, quantity 1) and a
  combine's unspent use item a `node.tool` child. A trainer recipe nobody
  has learned gets a **step node** instead (`node.step = { kind = "train",
  spellID, name, professionName, rank, trainer, who }`, key
  `<parent>>train:<spellID>`): not an item, so it claims nothing, has no
  options, route `train`, missing 1; `Summarize` counts it and lists it in
  `missingLeaves` with `step` / `name` and no `itemID`. Everything that walks
  a tree must allow `node.itemID == nil` for such nodes (shopping rows key
  them `train:<spellID>` in the "learn" category with the training cost as
  their price; CraftWise prices the step at the training cost in craft and
  hybrid; the Overview never lists it as a missing material). The planner no longer
  returns `RECIPE_NOT_LEARNED`: an unlearned recipe is planned as an obtain
  tree with `view.recipeStatus = "unlearned"` so the whole path is visible.
  Trainer requirements are not in the client's tables: `TrainerProvider`
  records them from trainer windows (`ForeverPathDB.trainers[spellID]`) and
  sets `Recipes.trainerLookup`; `Recipes.ApplyTrainer` raises `skill.min`
  to the recorded rank and attaches `recipe.trainer` when a recipe is
  decoded, and `Recipes.Invalidate` drops decoded recipes after a new visit.
- **Source hints**: `Planner.SourceFinder` chains `deps.data.Sources` (static
  table, still empty), `SourceProvider.Sources` (vendors, DungeonJournal,
  AtlasLoot, quest rewards, heuristics) and `CharacterProvider.Sources`
  (alts). The resolver picks the default route by
  `DependencyResolver.RouteRank` (vendor < alt < altcraft < gather < drop <
  quest < buy). A gathering material whose only recipes refine a lower tier
  of itself (`SourceProvider.IsRawMaterial`: gather class hint, every recipe
  has one reagent type of the same gathering kind and belongs to a profession
  other than the gathering skill) keeps its class hint and is marked
  `node.raw` by the resolver (`opts.isRaw`), which then never defaults to a
  craft for it; a "craft" override expands exactly one tier. Item classes
  come from the client or, when uncached, from the catalogue
  (`Recipes.ItemClass`). Gathering hints pass through `SourceProvider.QualifyGatherHint`:
  `GatherersFor(skill)` (this character's live professions, then alt
  snapshots) either names who can gather (`gatherer` = alt name, detail
  "<who> has <skill> (level)") or marks the hint `unavailable`, which the
  resolver's route choice, the shopping-list labels and the requirements
  tags skip. A ForeverDB or Wowhead export would land in `Data/` and need
  no other change.
- **Prices**: `PriceProvider.GetPrice` asks every registered source (vendor
  recorder, Auctionator) and returns the cheapest with the rest in
  `alternatives`; `GetMarket` is the AH price alone (used for "buy the
  finished item"). Market prices carry `scannedAt` (the account's last browse
  scan when seen today, otherwise now minus the age in days) and
  `Freshness` grades them fresh / aging / stale. Nothing is cached by
  ForeverPath; Auctionator's database is the store.
- **CraftWise**: `CraftWise.Compare(tree, { priceOf, marketOf })` walks the
  tree post-order. Per node: `buy` = price x missing, `craftPath` = buy every
  leaf below, `craft` = sum of the children's hybrid, `hybrid` = the cheaper
  of buy and craft (alt routes and owned stock cost 0; a gather/drop/quest
  route is priced at its AH price as what you would pay instead). Strategies
  for the root: `buy` (market price x quantity), `craft` (root craftPath),
  `hybrid` (root craft). `plan[itemID]` = "buy" or "craft" for every learned
  craftable component; `ApplyPlan` writes "buy" overrides and clears the
  rest, `Mode` tells which preset the goal's overrides match. The planner
  supplies `view.fullTree` (routes ignored, private ledger) when overrides
  exist so a bought subtree can still be compared.
- **Attunements**: `AttuneProvider.Progress(id)` resolves Attune's steps
  (Spacers dropped, ordered by STAGE then ID) and marks each done: Quest /
  Turn In from `Compat.IsQuestFlaggedCompleted`, Pick Up also from
  `Compat.IsOnQuest`, Level from `UnitLevel`, Item from bag + bank counts
  (`COUNT`), Kill / Interact / Click / Rep / Attune from `Attune_DB.toons`'s
  `done["<attune>-<step>"]`, End when all its FOLLOWS are done; then every
  predecessor of a done step is done. `current` = open steps whose
  predecessors are done, `next` = first non-side one. `Planner.EvaluateAttunement`
  wraps it in a view (`view.attunement`, synthetic `view.item`,
  `progress.percent`), `Overview` turns `next` into a recommended step and
  `GoalCompletion` completes the goal when `complete` is true.
- **DungeonJournal bridge**: `SourceProvider.IndexDungeonJournal` walks
  `_G.ForeverDungeonJournal_NS.DB[dungeon].bosses[].loot` (5th field = trash
  mob name), `.quests[].rewardItems` and `SHARED_BY_BOSS` into
  `journal.index[itemID]` (3 drops + 3 quests per item), lazily on the first
  source lookup. Hints carry `journal = true`, `boss`/`npcID`/`trash`/`shared`
  or `quest`/`questID`/`choice`/`faction`/`pickup`. AtlasLoot hints for a boss
  already listed by the journal are dropped.
- **Shopping list sources**: `ShoppingList.Build` classifies rows from
  `node.route`; vendor / gathering rows appear as soon as a source table
  feeds `DependencyResolver` hints of kind `vendor`, `gather` or `drop`.
- **CraftWise / pricing**: `PriceProvider.RegisterSource(name, { IsAvailable, GetPrice })`.
  Unknown prices are `nil`; engines must surface that instead of pricing at 0.
- **Other clients**: add fallbacks in `Core/Compat.lua` only. On a client with
  only the legacy tradeskill API the profession provider reports itself
  unavailable and the UI explains why.
